# pixel-art-tests primitives

> Primitives of `pixel-art-tests`, in one file at the project root. The integration branch is `main`. Status is `confirmed` or `inferred`; `pending <branch>` marks code that `main` does not have yet.

## sprite animation

- **`sprite manifest`**, `assets/<folder>/<id>-anim.json` and `assets/<folder>/<id>-anim.manifest.js`, confirmed
  Tells consumers how to cut and play the frames of one character sheet and its effect sheets. Each character writes `assets/<folder>/<id>-anim.*` (`.png`, `.json`, `.manifest.js`) and one `assets/<folder>/<id>-<effect>.png` per effect. `<folder>` is the config `out_dir`, and it does not have to be the id: `slime-drop` is in `assets/slime/`, `exterminator` is in `assets/exterminator/`. Never derive a manifest path from the id alone. Contract: keys `id`, `image`, `frameWidth`, `frameHeight`, `pivot {x, y}` (cell px from the cell top left corner) and `animations[{name, row, frames, fps, loop}]`, plus the optional top-level `effects{name: {image, frameWidth, frameHeight, frames, anchor {x, y}, hitboxes}}`. Every image path is relative to the folder of the manifest file, not to the project root or the page. The sheet has one row per animation, and all cells have the same size. Frame `i` of row `r` starts at `(i * frameWidth, r * frameHeight)`. A skipped animation has no row and the next rows move up, so find a row by `name`, never by index. Effect frames are in one row: frame `k` starts at `x = k * frameWidth` of that effect. `hitboxes` has one entry per effect frame, each a list of up to 4 rects `{x, y, w, h}` in effect-frame coords: vertical slices of the main flame body only, so detached embers are not in the hit area. Read hit areas from `hitboxes`, never from canvas pixels: under `file://` the canvas is tainted and pixel reads fail. Optional keys per animation: `stride` is the art px per cycle; move the game entity by `stride` toward +x for each cycle, or the character slides, and never hard-code it. `offsetY` has one int per frame, negative is up; it is manifest only, the pixels stay in the cell, and the pivot ignores it. `fx` has one entry per frame, `{effect, frame, x, y}` or null: draw frame `frame` of that effect so its `anchor` lands on `(x, y)` in cell coords plus the `offsetY` of that frame. Effects draw on top of the character. `phases` holds named inclusive frame ranges for the game (exterminator jump `takeoff`/`air`/`land` and attack `start`/`sustain`/`end`; slime attack `windup`/`strike`/`recover`, heavy `windup`/`air`/`impact`/`recover`, hurt `hit`/`recover` and death `remains`). `pivot` is the ground contact point. The body base row (the lowest opaque row) is the same row in every frame of every animation, and no pixel is below it. `pivot.y` is the line under the base row minus the config `ground_sink`. The exterminator has no sink, so no pixel is below its `pivot.y`. The slime sinks its bottom `GROUND_SINK` rows below `pivot.y`, into the floor surface; without the sink the soft body looks like it floats. A frame with `ty` (the slime heavy jump) lifts its pixels above the base row, so the base row can be empty in that frame. `pivot.x` comes from the idle pose: its bbox center (config `pivot: "bbox"`, slime) or the bottom center of its feet (`pivot: "feet"`, exterminator). Other poses align by the config placement: `center`, `back`, `feet` or `top_back` (the back of the tank, the exterminator default). Characters face +x. The exterminator `fire` is a separate effect, so its character cell covers only the character. Slime: rows are idle, crawl, attack, heavy, death, hurt; `crawl` stays in place and uses `stride`; `death` does not loop, and its `remains` phase (the last frame) is the held final state. `<id>-anim.manifest.js` is one line, `(window.SPRITE_ANIMS = window.SPRITE_ANIMS || {})["<id>"] = <JSON>;`. Keep it: pages open by `file://`, where `fetch` of a local JSON is blocked. Only [[PRIMITIVES#sprite frame generator]] writes these files: never edit an output by hand, and never hard-code cell size, pivot, effect size, effect anchor or hitboxes.
  Consumers: 2 (`sprite-viewer.html`; it loads each `.manifest.js` in its `MANIFEST_PATHS` by `<script>`, one at a time, reads `window.SPRITE_ANIMS[id]`, resolves image paths against the manifest folder, and reads all keys except `loop`, `stride`, `phases` and `hitboxes`. `mini-game.html`; it loads `assets/slime/slime-drop-anim.manifest.js` and then `assets/exterminator/exterminator-anim.manifest.js` by `<script>`, reads `window.SPRITE_ANIMS[id]`, resolves image paths against the manifest folder, finds animations by `name`, and reads `stride`, `phases`, `fx`, `effects[...].anchor` and `effects[...].hitboxes`, but not `offsetY`. Walk and crawl speed is `stride * fps / frames`, and the fps scales with the speed. Without the exterminator manifest it draws a built-in placeholder sheet. Without `hitboxes` it uses the full effect frame box as the hit area.)
- **`sprite frame generator`**, `tools/make-sprite-frames.py`, `tools/sprite_core.py` and `tools/characters/<id with _ for ->.py`, confirmed
  Builds the sheet, the effect sheets and the [[PRIMITIVES#sprite manifest]] of one character from its key-pose sheets. Contract: `python3 tools/make-sprite-frames.py <id>` (`--out-dir`, `--name`, `--contact`, `--contact-scale`, `--scale-tolerance`, `--grid WxH`) loads `CONFIG` from the character config and writes all outputs of that character together. Change a config and run it again; never edit an output by hand. Each run calculates cell size, pivot, effect size, effect anchor and `hitboxes` (`hitboxes()` in `sprite_core.py`) again from the frames. Key sheets are `-unslop.png` grids of `cols` x `rows` cells (default 2x2) in reading order. Each sheet is resized with nearest-neighbor to a common art grid before pose extraction: the config `grid`, or `round(canvas / (2048/449))` per axis from the raw canvas size `canvas`; `--grid WxH` overrides it. Keep one art pixel scale for all sheets of a character: pixel-unslop finds a different art pixel on each raw sheet. The slime sets `grid` to 449x301, not the canvas result 449x302, so its sheet does not change. The scale check stops the run, with nothing written, when a sheet does not match the idle art pixel scale. Its limit is `scale_tolerance` per sheet (default 0.08; `--scale-tolerance` overrides all). The slime death sheet has a wider limit because `death_hit` is drawn bigger on purpose. A missing sheet or effect skips the animations that need it. Animations are data: one `build_*` frame list per animation in the config, with transforms per frame (`F(...)`, optional `bob`, `offset_y`, `fx`, `layered`). The config hook `prepare(raw)` runs on the raw key poses before placement. The exterminator uses it to rebuild its walk from the 8-cell pose-guide sheet `assets/exterminator/keys/exterminator-keys-walk8-unslop.png` (4x2): the upper body of frame 1 goes on all 8 frames at the designed bob `WALK_BOB_PX`, the legs come from each frame, and a generated torn hem covers the seam. The walk `stride` is the foot spread of walk frames 1 and 5. The config `layers` per pose (exterminator idle) sets a waist row and a stretch band, region polygons with depth (tank, head, arms), and a pilot flame. The flame is cut out and flickers through variants that use only flame and fire-sheet colors. The frame key `layered {rise, dy{region}, flame}` drives it. The exterminator fire is split from the attack poses at one nozzle point per pose (`FIRE["nozzles"]`). The pixels right of the nozzle column are cut into components, and the component nearest the nozzle is the main flame. A cut piece that touches the character across the cut, away from the nozzle (a boot toe), goes back to the character. All other pieces (embers) stay in the `fire` effect. `hitboxes()` slices only the largest component of each effect frame with at least 6 px, so embers and stray bits never stretch the slices.
  Consumers: 2 configs (`tools/characters/slime_drop.py`, `tools/characters/exterminator.py`), plus `tools/rig_core.py` of [[PRIMITIVES#rig generator]], which imports `ROOT` and `rnd` from `sprite_core.py`.

## level art

- **`level assets manifest`**, `assets/level/level-tiles.json` and `assets/level/level-assets.manifest.js`, confirmed
  Tells the game how to cut the level tile sheet and draw the two parallax layers. Contract: `window.LEVEL_ASSETS = {id, tiles: {image, width, height, pieces: {name: [x, y, w, h]}, meta: {ground|stonePlatform|catwalkLeft|catwalkMid|catwalkRight: {surfaceY}, stonePlatform.chainRows}}, far: {image, width, height, parallax 0.15, repeat "mirror"}, mid: {image, width, height, parallax 0.45, repeat "plain", darken 0.3}}`. Image paths are relative to `assets/level/`. Pieces are ground, wall, stonePlatform, catwalkLeft, catwalkMid, catwalkRight, pipeValve, drainGrate, barrel, chainHook, bones, crate and drip1..3, plus the derived `groundTile` and `catwalkMidTile` (ends trimmed for repeat) and `wallUpper` (the wall rows above the pipe elbow, for vertical fill). `surfaceY` is the first row of a piece with at least 70% opaque pixels; the game puts the walkable top `TOP_INSET` (5) px below it. The tile sheet is the source resized with nearest-neighbor to 449x301, the same art px density as the sprites. The game reads `image` and `parallax` of each layer, mirrors the far layer by itself, and does not read `repeat` or `darken`. The mid darkening is already baked into `level-bg-mid.png`, so never apply `darken` again. Generator: `tools/make-level-assets.py` (python3 + Pillow) from `assets/level/src/level-tiles-unslop.png`, `level-bg-far-unslop.png` and `level-bg-mid-unslop.png`; it checks each piece box with connected components. Never edit an output by hand; change the script and run it again.
  Consumers: 1 (`mini-game.html`).

## skeletal rig

- **`rig manifest`**, `assets/<folder>/<name>.json` and `assets/<folder>/<name>.manifest.js`, confirmed
  Tells a page how to pose and draw one cutout character from a parts atlas, with no frame sheet. The full key contract is the docstring at the top of `tools/rig_core.py`. Each character writes `<name>.png` (the parts atlas), `<name>.json` and `<name>.manifest.js` in the config `out_dir`; black-knight writes `assets/black-knight/black-knight-rig.*`. `<name>.manifest.js` is one line, `(window.SPRITE_RIGS = window.SPRITE_RIGS || {})["<id>"] = <JSON>;`, so `file://` pages load it by `<script>`. Keep rigs in `window.SPRITE_RIGS`, never in `window.SPRITE_ANIMS`. Never add a rig to the `MANIFEST_PATHS` of `sprite-viewer.html`: its validator rejects an entry without `frameWidth`, `frameHeight` and `animations[]`. `image` is relative to the manifest folder. Model space: art px, origin on the ground line under the feet, +x forward, +y down, rotations in degrees, positive is clockwise on screen. `frame {w, h}` is one 1x canvas that holds every frame of every animation. `pivot` is the model origin in that canvas, the ground contact point. `frame.h` equals `pivot.y` when no pixel goes below the ground, so put `pivot` on the floor line. `animations` is an object keyed by name, not a list as in the sprite manifest. Each animation has `fps`, `frames`, `duration`, `loop` and `tracks`. `tracks` holds per bone `rot`/`x`/`y` keys `[t, v]`, added to the rest values and linear between keys. A loop wraps at `duration`; a one-shot holds its last key. Optional keys: `phases` (same meaning as in [[PRIMITIVES#sprite manifest]]), `stride`, `z` (draw order overrides), `bboxes` and `hitboxes`. `stride` is art px per cycle: move the entity at `stride / duration` px/s toward its facing, or the feet slide. `bboxes` has one `[x, y, w, h]` per frame: the opaque bounds in frame coords, facing +x. `hitboxes` has one entry per frame, null or `[{x, y, w, h}]` along the sword blade, in frame coords, facing +x. For facing -1, the left edge of a rect is `X - (r.x - pivot.x) - r.w`, with the pivot drawn at `X`. Read body and hit areas from `bboxes` and `hitboxes`, never from canvas pixels. A one-shot with a `hold` phase (black-knight `crouch` and `block`) is a held action. The page loops the `hold` range through the instance `time` while the key is down, then jumps to the exit phase (`up`, `lower`). The black-knight animation set and phases are in `ANIMATIONS` of `tools/rigs/black_knight.py`. Only [[PRIMITIVES#rig generator]] writes these files: never edit an output by hand.
  Consumers: 2 (`rig-runtime.js`, through `createRig`. `rig-viewer.html`; it loads `?manifest=<path>` or `assets/black-knight/black-knight-rig.manifest.js` by `<script>`, takes the first new key in `window.SPRITE_RIGS`, needs `bones`, `parts` and `animations`, resolves `image` against the manifest folder, and reads `stride`, `duration`, `fps`, `frames`, `phases`, `hitboxes` and `pivot`, but not `bboxes`.)
- **`rig generator`**, `tools/make-rig-assets.py`, `tools/rig_core.py` and `tools/rigs/<id with _ for ->.py`, confirmed
  Builds the parts atlas and the [[PRIMITIVES#rig manifest]] of one character from its cut parts and a config, and bakes every animation at build time. Contract: `python3 tools/make-rig-assets.py <id>` (`--out-dir`, `--contact DIR`, `--contact-scale`) imports `CONFIG` from `tools/rigs/<id with _ for ->.py` and writes the atlas, `.json` and `.manifest.js` together. Put rig configs only in `tools/rigs/`: `make-sprite-frames.py <id>` loads `tools/characters/<id with _ for ->.py` as a frame-sheet config. Change a config and run it again; never edit an output by hand. Config keys: `id`, `name`, `out_dir`, `master` (the whole character, for the rest check), `parts {name: {src, pivot, erase?}}`, `variants {name: {from, factor, tint}}`, `bones`, `rest`, `ik {chain: {thigh, shin, foot}}`, `followers` and `animations`. A part PNG must have alpha 0 or 255 only, or the run stops. `variants` bakes darkened copies into the atlas (the black-knight far limbs, `*_far`), so the runtime never tints. `rest` places each bone on the master, by `center` or `joint` plus a world `rot`. The tool then plants both feet flat on one ground row by IK, and moves the origin to the ground contact point, x at the center of the soles. An animation is data plus a `pose(t, frame, rig)` function that returns rot/x/y deltas per bone and an `ik {chain: target}`. The 2-bone leg IK (the knee bends toward +x) runs only at build time and is baked into rotation keys, so the runtime has no IK. `followers` adds a delayed share of one bone rotation to another bone (the tabards). `settle [first, last]` moves the lowest pixel of those frames onto the ground (a body that lies down). `stride: "feet"` calculates the stride from the planted feet; a number goes to the manifest as is. `hitbox {bone, from_x, frames, slices, pad}` bakes `hitboxes` along that bone, from `from_x` to the blade tip on the part pivot row. `bboxes`, `frame` and `pivot` come from renders of every frame. The checks only print `WARN` lines and the outputs are still written: a leg that misses its IK target, a planted flat foot that slides against the stride, and pixels below the ground line. Read the `WARN` lines after each run. `Rig.render` in `rig_core.py` is a Pillow copy of the draw math of [[PRIMITIVES#RigRuntime]] (FK, nearest-neighbor, 1x). Change both together, or the baked `bboxes`, `hitboxes`, `frame` and ground checks stop matching the screen. `--contact DIR` writes one `rigdev-<id>-<anim>.png` frame strip per animation and `rigdev-<id>-rest-check.png` (master, rest pose, overlay).
  Consumers: 1 config (`tools/rigs/black_knight.py`; it also imports `gait_foot`, `keyed`, `mat_apply`, `mat_rot`, `smooth`, `sole_points` and `wrap180` from `rig_core.py`).
- **`RigRuntime`**, `rig-runtime.js`, confirmed
  Plays [[PRIMITIVES#rig manifest]] animations in the browser and draws them on a canvas. Contract: plain `<script>`, no build step, works on `file://`; `window.RigRuntime = {createRig(manifest, image), createInstance(rig), sampleKeys(keys, t)}`. Instance API: `play(name, {restart, time, keepPhase})` returns false for an unknown name, and the same name without `restart` keeps playing. `keepPhase` keeps the cycle fraction between two loops (walk to sprint). `update(dt)` takes seconds already scaled by speed; a loop wraps at `duration`, and a one-shot stops at its end and sets `finished`. `render()` poses the bones (FK) and draws all parts on the 1x offscreen `canvas` of `frame.w` x `frame.h`, nearest-neighbor. `draw(ctx, x, y, scale, facing = 1)` puts the pivot on the art px `(x, y)`, rounded; `scale` is whole target px per art px, and `facing` -1 mirrors. Also `drawBones(ctx, x, y, scale, facing)`, `phase()`, `frameIndex()` and `sampleTime()`. Call `render()` once per tick, before `draw()` and `drawBones()`. Pages also use the fields `time` (writable, for hold loops), `anim`, `finished` and `stepped`. It never reads pixels. `stepped` is true by default: frame `i` holds from `i / fps` to `(i + 1) / fps`, the poses the tool baked and checked. With `stepped` false it samples between baked frames, which the tool checks do not cover. With `stepped` on, a page that moves the entity on each tick draws it on the ground at `x - (time - sampleTime()) * speed`, or the planted foot slides inside a held frame.
  Consumers: 1 (`rig-viewer.html`; it uses the full instance API and writes `time` to loop hold phases).
